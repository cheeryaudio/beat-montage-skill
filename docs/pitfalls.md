# ffmpeg 色度损坏与管道死锁 —— 排查实录

在本机（Windows 11，imageio-ffmpeg 7.1 与 BtbN master N-127021 2026-09-30 双构建）开发
卡点混剪管线时，遭遇"成片整体变绿"与"渲染永久挂起"两类问题。以下是完整的定位过程与结论，
供遇到同类问题的人参考。

## 症状

1. 成片**整体变绿**：YUV 平面统计 U 均值 ≈ 61、V 均值 ≈ 67（正常中性画面 ≈ 128），
   且数值**确定性复现**（同图同输入 → 完全相同的错误输出）。
2. 渲染管线在 ~700 帧处**永久挂起**：输出文件停止增长，ffmpeg/python 进程全部存活。

## 定位过程（可复用的方法论）

对嫌疑滤镜图做**逐层前缀渲染**：把 filter_complex 按段拆开，从最短前缀开始逐层累加，
每层渲染 1 帧并统计 RGB 均值（警惕：抽帧验证时 mkv 解码路径与 rawvideo 路径可能给出
**不一致**的结果，两条路径都要看）。

### 变绿的真凶

- `blend`（任意模式）的输出**不经过帧重分配**直接串接 `overlay`（或任何触发
  rgb→yuv 转换的滤镜）→ 色度平面被错误数据覆写。
- **上游真 bug**：在 BtbN master N-127021 (2026-09-30) 上同样复现，与线程数无关
  （`-filter_threads 1` 不能修复）。
- **修复：每个 blend 之后立即插入 `scale=W:H` 屏障**，强制重分配帧缓冲。
  实测屏障前后一绿一正常，立竿见影。

### 易被误导的假象（我们为此多花了几个小时）

- **zoompan / eval=frame 动态尺寸 overlay 链**：症状与真凶高度相似，但单独测试是干净的——
  它只是"常与 blend 邻接出现"的巧合关联。如果 barrier 修复后仍绿，再查它。
- **忘加 `-f concat`**：`-i list.txt` 被探针识别成 `ansi` 视频（640x400 pal8）喂进滤镜图，
  尺寸不匹配报错或产生完全无关的绿色画面。所有对照实验必须带齐 `-f concat`。
- **素材本身是 60fps**：逐秒亮度扫描如果不加 `fps=30` 归一化滤镜，时间戳错位一倍，
  " brightest at 207s " 其实是 62.5s。

## 挂起的真凶

- **ffv1 中间文件**（新 master 构建编码）：解码在 ~650-750 帧处确定性卡死
  → 大型滤镜图的中间产物不要用 ffv1 mkv；让调色直接进 rgb24 管道。
- **`dec.wait()` 死锁**：concat 流读完全部所需帧后，解码器仍会尝试写下一段而阻塞，
  python 端 `dec.wait()` 永久挂起 → 读完全部帧后**直接 `dec.kill()`**。
- **活管道编码**（解码管道 → PIL → x264 stdin）：x264 中途停转消费会反压堵死整条链
  → 解码与编码之间用**磁盘文件交接**（rgb24 raw 约 5GB/分钟，用完即删），
  或使用带 buffer 的线程模型。

## 防御性写法（最终稳定形态）

```
ffmpeg -f concat -i list.txt -vf "<调色, 无 blend>" -f rawvideo -pix_fmt rgb24 -
    │ (python: 逐帧读入 → PIL alpha_composite 动画序列 → 数值淡入淡出)
    └─ 写入 passB.rgb (磁盘)
ffmpeg -f rawvideo -pix_fmt rgb24 -i passB.rgb -i mix.m4a → x264 mp4
```

所有动画（文字砸入/缩放脉冲/旋转/印章/粒子）在 PIL 里逐帧预渲染成全画布 RGBA 序列，
ffmpeg 图内只做恒定尺寸叠加——兼顾表现力与确定性。
